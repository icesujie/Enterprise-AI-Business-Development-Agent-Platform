# 企业知识文档治理差距分析

## 1. 目的和审查范围

本次审查用于判断：在启用 Knowledge Retrieval 之前，Phase 2.5.1 知识管理控制面和 Phase 2.5.2 处理流水线是否已经具备充分的企业文档治理能力。

评估基于截至 2026-08-14 的实际实现，主要包括：

- `apps/api/src/sari_api/adapters/models.py`
- `apps/api/src/sari_api/adapters/enterprise_knowledge_repository.py`
- `apps/api/src/sari_api/api/routes/knowledge_management.py`
- `apps/api/src/sari_api/domain/identity.py`
- `apps/web/src/app/(workspace)/knowledge/`
- 迁移 `6b2a8e4d1c90` 和 `a7d4c2e91f63`
- Phase 2.5.1 和 Phase 2.5.2 集成测试

本文只做差距分析并提出实施建议，不修改应用代码、API、权限或数据库结构。

### 评级定义

| 评级 | 含义 |
|---|---|
| 已支持 | 数据模型、API 或服务行为、授权和可用操作流程都已经存在 |
| 部分支持 | 已有部分数据或行为，但端到端治理能力不完整 |
| 未支持 | 不存在安全的应用操作流程 |

## 2. 结论摘要

当前系统已经形成可靠的“受审批控制的上传基础”，但还不是完整的企业文档治理系统。系统可以创建包含不可变版本 1 的逻辑文档，记录基础审核决定，把文档绑定到同业务域智能体，启用、处理和归档文档。受管知识表已经由租户 RLS 保护。

系统目前不能修改文档元数据、上传版本 2 及以上、恢复已归档文档、禁用绑定、查看以文档为中心的审计时间线，也不能回滚到历史内容。上传、审批、发布、绑定和归档全部共用宽泛的 `knowledge:manage` 权限，因此无法强制执行职责分离。

建议采用以下准入顺序：

```text
Phase 2.5.2 处理流水线
        ↓
Phase 2.5.3 治理补全
        ↓
Knowledge Retrieval
```

在系统可以可靠确定准确发布版本、授权状态和治理历史之前，不应向普通用户开放检索。

### 能力汇总

| 范畴 | 能力 | 评级 | 当前证据 | 主要差距 |
|---|---|---:|---|---|
| CRUD | 创建或上传 | 已支持 | 上传时创建逻辑文档和不可变版本 1 | 不能只创建元数据草稿 |
| CRUD | 修改元数据 | 未支持 | 元数据只在首次上传时接收 | 没有 PATCH API、UI、并发控制和变更审计 |
| CRUD | 替换文档版本 | 未支持 | 已有版本表和 `current_version_number` | 没有版本上传命令或状态重置 |
| CRUD | 归档 | 已支持 | 已批准或已启用文档可以归档 | 不要求原因；没有归档责任人字段 |
| CRUD | 恢复 | 未支持 | 当前服务把已归档状态当作终态 | 没有安全迁移或重新发布要求 |
| 责任归属 | 创建人、上传人、审批人 | 部分支持 | 已保存 ID 和核心时间 | 不返回版本上传人；没有修改人、发布人、归档人字段 |
| 审计 | 上传、审批、生命周期 | 部分支持 | 成功命令会写入 `audit_events` | 没有文档审计 API/UI，事件快照不足，不记录失败尝试 |
| 审计 | 绑定历史 | 部分支持 | 已审计创建绑定 | 不能禁用或重新启用，也没有历史视图 |
| 版本 | 版本号和历史 | 部分支持 | 已有不可变记录和仓储列表方法 | 没有公开的版本列表接口或 UI |
| 版本 | 当前启用或发布版本 | 部分支持 | 已有当前编号和生命周期状态 | 没有明确的 `published_version_id` 权威指针 |
| 版本 | 回滚 | 未支持 | 没有命令 | 必须保持不可变并重新审批 |
| RBAC | 上传、审批、发布分离 | 未支持 | 管理员拥有宽泛的 `knowledge:manage`；销售只读 | 同一个管理员可以完成所有关键动作 |

## 3. 文档 CRUD 分析

### 3.1 创建

**评级：已支持，但定义较窄。**

`POST /api/v1/knowledge-management/collections/{collection_id}/documents` 会保存私有对象、创建 `managed_knowledge_documents`、创建 `knowledge_document_versions` 版本 1、记录 SHA-256 和大小、写入 `created_by`，并生成 `knowledge.document.uploaded` 事件。

优点：

- 对象键以租户为前缀。
- 验证文件类型和大小。
- 版本记录不可变并包含内容指纹。
- 数据库事务失败时会清理对象。
- 使用租户 RLS 和明确租户查询条件。

限制：

- 创建和首次上传是同一个动作，不能只创建元数据草稿。
- 对版本 1 而言，上传人与逻辑文档创建人必然是同一用户。
- 重试上传没有幂等键保护。
- 当前实现没有病毒扫描或隔离状态。

### 3.2 修改元数据

**评级：未支持。**

逻辑文档保存了 `title`、`document_type`、`language` 和 `document_metadata`，但仓储方法、API 和 UI 都不能修改它们。集合元数据同样只能在创建时填写。

需要的治理行为：

- 允许在 `draft`、`uploaded` 或 `review` 状态下受控修改。
- 明确哪些变更会使审批失效。标题格式可能不影响审批，但语言、文档类型、分类、生效时间或证据范围应该影响。
- 使用现有记录 `version` 字段和 `If-Match` 实施乐观并发控制。
- 审计修改前后值，但不能把敏感文档原文放入事件。
- 当影响检索的元数据改变时，重置已处理资产。

### 3.3 替换文档版本

**评级：未支持。**

数据库结构可以保存多个不可变版本，仓储也已有 `list_versions()`，但应用只会创建版本 1。当前没有上传新版本 API、当前版本切换、审批重置、版本列表路由或版本历史 UI。

替换版本必须：

1. 锁定逻辑文档。
2. 把新字节保存到新的不可变对象键。
3. 创建版本 `N + 1`，保存独立上传人、指纹、元数据和时间。
4. 设置 `current_version_number = N + 1`。
5. 把生命周期重置为 `uploaded`、审批重置为 `pending`、处理状态重置为 `uploaded`。
6. 撤销被取代版本的发布资格。
7. 保留所有旧版本、决定、处理运行、分块和引用作为历史证据。

### 3.4 归档

**评级：已支持，但企业治理仍不完整。**

已批准或已启用的当前文档可以进入 `archived`，并写入审计事件。未来处理已经会拒绝已归档文档。

差距：

- 不要求或保存归档原因。
- 没有正式的 `archived_by` 和 `archived_at` 字段。
- 现有智能体绑定仍然保持启用；未来检索可通过生命周期过滤保证安全，但明确撤销更容易理解。
- 当前版本状态会变成已归档，但没有明确的发布版本指针可以清空。
- 没有测试证明未来检索绝不会返回已归档分块。

### 3.5 恢复

**评级：未支持。**

已归档文档没有任何向外的生命周期迁移。安全恢复应当把文档送回 `approved`，而不是直接回到 `active`，并要求执行一次明确发布。如果审批已经过期、策略改变或底层版本不再合格，则应该回到 `review`。

恢复操作绝不能静默重新启用旧绑定，也不能让过期分块重新具备检索资格。

## 4. 用户责任归属分析

### 4.1 当前保存的责任信息

| 记录或动作 | 当前责任信息 |
|---|---|
| 创建集合 | `knowledge_collections.created_by`、`created_at`、`updated_at` |
| 创建逻辑文档 | `managed_knowledge_documents.created_by`、`created_at`、`updated_at` |
| 上传版本 | `knowledge_document_versions.created_by`、`created_at` |
| 审批 | 批准决定保存 `approved_by`、`approved_at`、`review_note` |
| 拒绝 | 执行人只存在于通用审计事件中 |
| 创建绑定 | 绑定保存 `created_by`、`created_at`，审计事件也有执行人 |
| 启用或归档 | 执行人和时间只存在于审计事件中 |
| 请求处理 | 处理运行保存 `created_by`、`created_at` 和关联 ID |

### 4.2 责任归属差距

- `VersionResponse` 不返回 `created_by`，所以用户看不到版本上传人。
- `BindingResponse` 不返回 `created_by`。
- 知识管理 UI 不会把 ID 解析为安全的显示名称。
- 受控资源没有 `updated_by`、`submitted_by/at`、`published_by/at`、`archived_by/at` 或 `restored_by/at`。
- 被拒绝的决定没有文档或版本级正式审核人和时间。
- 审批在逻辑上属于准确版本，但当前审批字段位于逻辑文档。出现版本 2 后含义会变得模糊。
- 没有用于后台治理事件的明确系统或服务执行人表示。

## 5. 审计跟踪分析

### 5.1 当前写入的事件

控制面 API 会为以下成功操作记录事件：

- 创建集合。
- 上传版本 1 文档。
- 提交审核。
- 批准或拒绝。
- 创建智能体绑定。
- 启用。
- 归档。
- 请求处理。

每条事件包括租户、执行人、动作、目标、结果、关联或请求 ID、详情和时间。

### 5.2 审计差距

**评级：部分支持。** 系统会创建事件，但尚未形成可用的治理轨迹。

- 没有 API 或 UI 按文档或准确版本列出审计事件。
- 元数据修改、新版本、禁用或重新启用绑定、恢复、回滚、明确发布都没有事件，因为相应命令不存在。
- 审批事件没有一致保存准确 `document_version_id`、版本号、指纹或被审核内容指纹。
- 生命周期事件没有保存旧状态、新状态、原因或准确发布版本。
- 绑定事件没有保存绑定 ID 或旧状态和新状态。
- 只记录成功操作；被拒绝或无效的关键操作尝试不会成为治理安全事件。
- 通用 `audit_events` 表没有使用受管知识表采用的强制租户 RLS，而且当前不存在知识审计读取边界。
- 追加不可变只是应用约定，没有数据库强制保证。
- 尚未实施保留、导出、法律保全或防篡改策略。

启用检索前的最低要求，是提供按租户隔离、以文档为中心的只读审计接口，并让事件载荷完整指向准确版本。强加密防篡改和法律保全可以保留为后续合规增强。

## 6. 版本管理分析

### 6.1 版本号

**评级：部分支持。** 数据库强制 `(tenant_id, document_id, version_number)` 唯一，保存不可变对象键和指纹，并维护 `current_version_number`。API 详情只显示当前版本，现有仓储列表方法没有公开。

### 6.2 当前启用或发布版本

**评级：部分支持。** `lifecycle_status = active` 和当前版本状态可表示启用，但没有明确的不可变 `published_version_id`。当版本替换和回滚出现后，数字指针加可变生命周期状态不足以长期充当检索权威。

推荐的事实来源：

```text
逻辑文档
  ├── current_version_id    → 正在编辑或审核的版本
  └── published_version_id  → 可供检索的准确版本，或 NULL
```

检索必须使用 `published_version_id`，不能只使用最大版本号。

### 6.3 回滚

**评级：未支持。**

回滚不应把指针简单向后移动并假装历史没有发生。建议的命令应当从选定历史对象和元数据复制生成版本 `N + 1`，记录 `restored_from_version_id`，并让新版本重新经历审核和发布。这样能保持版本号单调增加，也能保证引用含义明确。

## 7. RBAC 分析

### 7.1 当前权限

当前 MVP 只有两个角色：

| 角色 | 知识权限 | 实际能力 |
|---|---|---|
| `admin` | `knowledge:manage`、`knowledge:retrieve` | 创建集合、上传、提交、批准或拒绝、绑定、启用、归档、处理和读取 |
| `sales` | `knowledge:retrieve` | 列出和查看元数据或状态 |

所有修改操作都使用 `knowledge:manage`。因此系统不能独立回答：

- 谁可以上传？
- 谁可以审批？
- 谁可以发布？

目前三个问题的答案都是“任何租户管理员”，而且可以是同一个人处理同一份文档。

### 7.2 需要拆分的权限

Phase 2.5.3 应引入以下明确权限，并暂时只把 `knowledge:manage` 保留为兼容聚合权限：

| 权限 | 目标操作 |
|---|---|
| `knowledge:read` | 查看集合、文档、版本、绑定和允许查看的审计历史 |
| `knowledge:upload` | 创建文档、修改允许的元数据、上传替换版本 |
| `knowledge:submit` | 提交准确当前版本审核 |
| `knowledge:approve` | 批准或拒绝准确版本 |
| `knowledge:bind` | 启用或禁用智能体绑定 |
| `knowledge:publish` | 按策略启用或发布、归档和恢复 |
| `knowledge:process` | 请求处理符合条件的准确版本 |
| `knowledge:audit_read` | 读取治理事件 |

未来企业角色模型的建议意图：

| 角色 | 上传 | 审批 | 发布 | 读取 |
|---|---:|---:|---:|---:|
| Tenant Admin | ✓ | ✓ | ✓ | ✓ |
| Sales Manager | 可选 | 审批业务资料 | 发布业务资料 | ✓ |
| Sales User | 可选创建草稿或上传 | — | — | ✓ |
| Technical User | 上传技术资料 | 按技术策略审批 | 默认不允许 | ✓ |
| Viewer | — | — | — | ✓ |

对当前双角色 MVP，可以先把所有新权限授予 `admin`，并保留 `sales` 只读，从而维持 Phase 1 行为。但是，当租户启用职责分离策略时必须禁止自我审批；在真正多租户使用前，应引入更完整的企业角色。

## 8. Knowledge Retrieval 之前的风险

| 风险 | 严重程度 | 影响原因 |
|---|---:|---|
| 没有明确发布的准确版本 | 严重 | 检索可能使用错误或已被取代的内容 |
| 没有版本替换和发布流程 | 高 | 纠错时只能另建逻辑文档，无法治理 |
| 没有恢复或回滚 | 高 | 运维恢复容易演变为直接修改数据库 |
| 只有一个宽泛管理权限 | 高 | 上传人可以批准并发布自己的内容 |
| 用户看不到审计历史 | 高 | 审核人员无法确认来源或重建决定过程 |
| 审批字段只在逻辑文档 | 高 | 版本 2 出现后审批含义不明确 |
| 不能禁用绑定 | 高 | 无法明确撤销智能体授权 |
| 不能修改元数据 | 中 | 错误分类或语言无法安全修正 |
| 没有乐观并发和幂等 | 中 | 并发命令或重试可能造成治理状态不一致 |

## 9. Phase 2.5.3 实施计划

### 9.1 目标

补全未来检索所需的最低企业文档治理控制面，使检索具备确定性、可撤销性、责任归属和可审计性，但不实现检索或对话助手。

### 9.2 里程碑 A — 数据结构和不变量

新增非破坏性迁移：

1. 为受管文档增加 `current_version_id` 和可空的 `published_version_id`，过渡期间保留 `current_version_number`。
2. 增加版本级审批字段：`review_status`、`reviewed_by`、`reviewed_at`、`review_note` 和可选的 `restored_from_version_id`。
3. 增加文档治理责任字段：`updated_by`、`published_by/at`、`archived_by/at` 和归档或恢复原因。
4. 为绑定增加 `updated_by/at`；禁用绑定时保留原记录而不是删除。
5. 增加版本和文档租户一致性以及发布版本归属约束；PostgreSQL 无法安全直接强制的部分由应用校验补充。
6. 为治理审计读取路径增加租户 RLS，并增加文档或版本时间线索引。

现有版本 1 文档应回填 `current_version_id`，指向当前版本。现有已启用文档应让 `published_version_id` 指向准确的已批准版本。迁移不重写任何文档字节。

### 9.3 里程碑 B — 应用服务和状态机

实现以下强类型事务命令：

- 使用 `If-Match` 修改允许的元数据。
- 上传替换版本 `N + 1`。
- 列出和查看所有不可变版本。
- 提交准确版本审核。
- 批准或拒绝准确版本。
- 发布准确的已批准版本。
- 归档已发布文档。
- 把已归档文档恢复为 `approved` 或 `review`，绝不直接恢复为已发布。
- 从历史版本创建新版本实现回滚。
- 禁用和重新启用智能体绑定。

关键命令应当在适当情况下要求原因、支持幂等、锁定逻辑文档、验证租户或业务域或智能体一致性，并在同一事务中记录准确的状态前后值。

### 9.4 里程碑 C — API 契约

建议接口：

| 方法 | 端点 | 用途 |
|---|---|---|
| `PATCH` | `/api/v1/knowledge-management/documents/{id}` | 使用 `If-Match` 修改允许的元数据 |
| `POST` | `/api/v1/knowledge-management/documents/{id}/versions` | 上传不可变替换版本 |
| `GET` | `/api/v1/knowledge-management/documents/{id}/versions` | 列出完整版本历史 |
| `GET` | `/api/v1/knowledge-management/documents/{id}/versions/{version_id}` | 查看一个准确版本 |
| `POST` | `/api/v1/knowledge-management/documents/{id}/versions/{version_id}/submit-review` | 提交准确版本审核 |
| `POST` | `/api/v1/knowledge-management/documents/{id}/versions/{version_id}/approval` | 批准或拒绝准确版本 |
| `POST` | `/api/v1/knowledge-management/documents/{id}/versions/{version_id}/publish` | 发布准确的已批准版本 |
| `POST` | `/api/v1/knowledge-management/documents/{id}/archive` | 填写原因并撤销发布 |
| `POST` | `/api/v1/knowledge-management/documents/{id}/restore` | 恢复到未发布状态 |
| `POST` | `/api/v1/knowledge-management/documents/{id}/versions/{version_id}/rollback` | 从历史版本创建后继版本 |
| `PATCH` | `/api/v1/knowledge-management/documents/{id}/bindings/{binding_id}` | 启用或禁用绑定 |
| `GET` | `/api/v1/knowledge-management/documents/{id}/audit-events` | 读取文档治理时间线 |

在 UI 迁移期间，可以暂时保留预生产旧生命周期端点作为兼容包装器，但它们必须调用相同的版本感知服务。

### 9.5 里程碑 D — RBAC 和策略

1. 增加第 7.2 节中的明确权限。
2. 初期把当前 `admin` 映射到所有治理权限，把当前 `sales` 映射为只读，从而保持 Phase 1 行为。
3. 增加 `uploader_user_id != approver_user_id` 策略钩子，并支持可选的发布人分离。
4. 根据准确版本指纹检查审批和发布授权。
5. 对所有未知或缺失权限默认拒绝。

### 9.6 里程碑 E — 审计和 UI

扩展 `/knowledge`：

- 增加文档详情页，不再只依赖列表行按钮。
- 增加可编辑元数据面板和并发冲突提示。
- 增加版本历史，显示上传人、指纹、状态、决定和发布状态。
- 只向获得授权的人显示审批和发布操作。
- 增加智能体绑定面板及启用或禁用历史。
- 增加只读文档时间线，合并上传、元数据、审核、审批、绑定、处理、发布、归档、恢复和回滚事件。
- 清楚区分当前版本和已发布版本。

审计载荷应包含 ID、安全元数据差异、指纹、状态迁移、执行人、原因和关联 ID，但绝不能包含文档原文、凭据或存储键。

### 9.7 里程碑 F — 测试和验收

必须验证：

- 并发上传时版本号仍然单调递增。
- 对象或数据库失败不会遗留孤立状态，也不会产生半完成的当前版本。
- 替换操作使审批失效，同时不修改旧版本。
- 发布只能选择具有合格绑定的准确已批准版本。
- 归档立即取消检索资格，同时保留分块和历史。
- 恢复绝不直接重新发布。
- 回滚创建新版本，并要求重新审批。
- 已禁用绑定不能处理或检索。
- 上传、审批、发布和读取审计权限分别得到执行。
- 配置禁止自我审批时，操作会被拒绝并记录审计。
- 每个治理命令都在同一事务中生成一条具有关联信息的审计事件。
- 跨租户文档、版本、绑定和审计访问不返回任何数据。
- 现有 Sari Arta 和 IVC 演示文档可以迁移，且不改变 CRM 或 Agent Playground 行为。

### 9.8 推荐实施顺序

```text
1. 迁移和数据回填
2. 版本感知仓储和服务
3. 权限拆分和策略检查
4. 版本、元数据和绑定 API
5. 发布、归档、恢复和回滚命令
6. 审计时间线 API
7. 知识文档详情 UI
8. 集成、RLS、并发和回归测试
9. 中英文文档和演示数据更新
```

## 10. Phase 2.5.3 验收门槛

当获得授权的审核人员只使用产品就能回答以下问题时，Phase 2.5.3 才算完成：

1. 谁在什么时候上传了这份准确内容？
2. 哪些元数据发生过变化、由谁修改、原因是什么？
3. 哪个准确的不可变版本获得了批准？
4. 谁批准、谁发布了它？
5. 哪些智能体当前可以访问，谁修改过这些权限？
6. 文档是已归档、已恢复、已被取代还是已回滚？
7. 系统能否证明不合格版本不能被处理或检索？

只有当这些问题都有确定且按租户隔离的答案后，Knowledge Retrieval 才应把 `published_version_id` 和已启用绑定作为强制过滤条件。

## 11. 明确不在范围内

Phase 2.5.3 不应实现：

- 向量相似度搜索或混合检索。
- 对话式 Knowledge Assistant。
- 由 AI 自动审批或发布。
- OCR、文档脱敏、DLP、法律保全或档案管理认证。
- 对外客户沟通。
- 修改 CRM、Agent Playground 或资格评估流程。
