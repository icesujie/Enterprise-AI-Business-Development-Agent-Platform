# Phase 3.2 营销内容业务验收

**状态：** 已准备受控人工验收；尚未获得最终 GO  
**验收数据集：** `phase_3_2_business_acceptance_v1`  
**工作区：** `/marketing-content/acceptance`  
**边界：** 仅供内部审核；不发布、不发送、不排期、不执行活动自动化，也不写入 CRM

## 1. 目的

本验收步骤用于判断受治理的营销内容智能体草稿是否能被 Sari Arta 业务审核人员实际使用。它不会引入另一套审批系统。所有编辑、审核提交、决定、反馈记录和批准继续使用现有 Content Governance 生命周期和 RBAC 控制。

## 2. 固定验收集

固定验收集包含十个合成且不敏感的案例。五种支持的内容类型各有一个英文案例和一个中文案例。

| # | 内容类型 | 英文场景 | 中文场景 |
|---:|---|---|---|
| 1–2 | Website Article | Indonesia school central kitchen project | 印度尼西亚学校中央厨房项目 |
| 3–4 | TikTok Script | School canteen renovation | 学校食堂翻新 |
| 5–6 | Instagram Reel Script | Factory canteen | 工厂员工食堂 |
| 7–8 | Facebook Post | Hospital and institutional kitchen | 医院及机构厨房 |
| 9–10 | Email Draft | Central kitchen capacity planning | 中央厨房产能规划 |

源文件是 `apps/api/src/sari_api/evaluation_data/marketing_business_acceptance_cases.v1.json`。请求使用现有 `content_requests.constraints` 中的数据集和案例标识进行标记。系统不创建验收专用数据库表，也不创建平行生命周期。

## 3. 审核人员工作流

```text
固定 Mock 草稿
→ 打开准确的受治理资产
→ 记录结构化人工反馈
→ 编辑并创建不可变人工后继版本
→ 提交准确版本和校验和进行审核
→ 独立审批人批准或拒绝
→ 验收汇总更新
```

内容作者和审批人必须是不同用户。创建者不能批准自己的资产。审核人员使用 `/marketing-content/{asset_id}` 上的现有控件：

1. 对准确当前版本**记录反馈**。
2. 使用**保存为新版本**保留 AI 草稿并创建人工后继版本。
3. 使用准确版本/校验和**提交审核**。
4. 由另一个拥有 `content:approve` 权限的用户登录并执行**批准**或**拒绝**。

拒绝、编辑、回滚和批准继续保留现有不可变历史与审计记录。

## 4. 人工修改比例

只有同时满足以下条件时才计算 Human Edit Distance：

- 资产存在由生成运行创建的 `ai_generated` 版本；
- 批准版本的来源是 `human`；
- 批准版本是从该生成版本派生的后继版本；
- 该准确人工后继版本是资产的批准版本。

界面显示修改百分比、AI 生成版本号和人工批准版本号。直接批准 AI 版本、批准回滚版本或不存在人工批准后继版本时都不返回指标。系统不会用虚假的零值代表缺失的人工审核。

## 5. 验收汇总

`GET /api/v1/content/acceptance` 和 `/marketing-content/acceptance` 显示：

- 案例总数、已准备、已审核、已批准和已拒绝数量；
- 真实平均人工修改比例；
- AI 生成版本和人工批准版本指针；
- 常见反馈类别；
- 确定性质量指标平均值；
- 品牌指南验证状态；
- OpenAI 对比状态。

该投影按租户隔离，要求 `content:read`，并从现有受治理请求、资产、版本、决定、反馈和生成运行中派生。

## 6. 品牌指南检查点

**品牌指南验证：Pending。**

本里程碑尚未收到经过批准的真实 Sari Arta 品牌指南。合成定位和确定性品牌契合评分不等于最终品牌批准。在授权的 Sari Arta 审核人员通过受治理知识流程批准真实指南之前，系统不得声称已经完成最终品牌验证。

Phase 3.2 最终 GO 前，业务负责人必须选择：

1. 使用已批准的真实品牌指南完成验证；或
2. 在生产激活前明确把缺少指南作为已记录的前提条件接受。

本验收包不会编造品牌规则。

## 7. 受控 OpenAI 对比

Mock 继续作为默认值。当配置的营销内容提供方不是 `mock` 时，验收准备操作会被禁用。因此，准备固定十项验收集不会有意触发付费提供方。

真实提供方对比必须由人工明确执行，并限制为第一组中英文配对案例：

```bash
cd apps/api
MARKETING_CONTENT_PROVIDER=openai \
OPENAI_API_KEY=... \
PYTHONPATH=src .venv/bin/python -m sari_api.marketing_generation_eval \
  --allow-paid-provider --max-cases 2
```

审核人员比较质量、事实依据、结构有效性、延迟以及提供方/模型。当当前 Provider 合同无法提供可靠用量或费用时，结果会标记不可用。不得把 API Key 放入源代码、截图、验收记录或聊天。

当前状态：**尚未执行**。只有记录业务原因后才可明确延期。

## 8. 最终 GO 标准

只有满足以下条件，Phase 3.2 才获得最终 GO：

- 十个验收案例全部完成审核；
- 不再包含不受支持的事实声明；
- 引用完整率保持 100%；
- 租户、RBAC、知识策略和智能体边界没有失败；
- 人工审核人员认为五种内容类型均可使用；
- 至少记录一个真实人工修改比例，并能看到配对版本；
- 英文和中文输出都被接受；
- 品牌指南验证已完成，或已明确接受为已知前提条件；
- 一个英文和一个中文的受控 OpenAI 对比已完成，或已明确记录延期原因。

最终 GO 是人工业务决定。自动评分不能批准内容，也不能批准本阶段。

## 9. 准确人工验收步骤

1. 保持 `MARKETING_CONTENT_PROVIDER=mock`，启动正常的 API、Worker、Web、PostgreSQL、Redis 和已批准合成公开知识演示服务。
2. 以内容作者身份登录并打开 `http://localhost:3000/marketing-content/acceptance`。
3. 点击一次**准备 10 项验收草稿**。刷新页面，直到十个案例都出现资产链接。该操作具有幂等性，会跳过已经存在或正在运行的案例。
4. 对每个案例点击**打开审核**。
5. 检查渠道结构、声明、证据、引用、CTA、中英文质量和业务实用性。
6. 至少记录一个结构化反馈类别，并可填写审核说明。
7. 编辑草稿并点击**保存为新版本**。不要覆盖或直接批准原始 AI 版本。
8. 对准确人工后继版本点击**提交审核**。
9. 使用另一个授权审批人账户登录，批准或拒绝准确审核版本及其校验和。
10. 返回 `/marketing-content/acceptance`，检查数量、版本指针、人工修改比例、常见反馈和质量汇总。
11. 完成品牌指南检查，或明确记录并接受该前提条件。
12. 可选择执行受控双案例 OpenAI 对比，并记录结果或延期原因。
13. 确认所有最终 GO 标准。只有这时项目负责人才能把 Phase 3.2 标记为已验收并更新 CHANGELOG。

不要自动开始 Phase 3.2.4。
